# ITSM 티켓 도구 협업 구성안

## 구성 원칙

이 구성은 `scope-document.md`의 단일 기능 경계, `intent-backlog.md`의 안전 경계 우선 순서, `feasibility-assessment.md`의 보안·회귀 위험을 따른다. 실제 조직을 새로 만들기 위한 계획이 아니라, 현재 AI-DLC 역할 팀이 각 단계에서 어떤 관점을 책임지고 요청자 및 내부 자문자와 어떻게 협업할지를 정의한다.

## 기본 협업 팀

### ITSM 티켓 도구 교차기능 팀

| 구분 | 역할 | 책임 |
|---|---|---|
| 제품 책임자 | 요청자 | 사용자 가치, 범위, 우선순위, 최종 승인 |
| 조율자 | 전달 책임자 | 목표 정렬, 흐름·의존성·차단 사항 관리 |
| 주 탐색자 | 아키텍처 책임자 | 기존 구조, 경계, 계약과 변경 영향 검토 |
| 실행 주도 | 개발 책임자 | 승인된 설계에 따른 기능과 테스트 구현 |
| 안전 탐색자 | 보안·DevSecOps 책임자 | 위임 권한, 비밀 보호, 오류 안전성 검토 |
| 검증 탐색자 | 품질 책임자 | 수용 기준, 계약·통합·회귀 증거 검토 |
| 필요 시 자문 | ITSM 운영 책임자 | 계약 또는 실제 운영 의미가 불명확할 때 확인 |

디자인, AWS 플랫폼, 배포, 운영 전문 역할은 이번 범위에서 상시 구성원이 아니다. 후속 단계에서 기존 화면·인프라·배포 경계에 예상 밖 변경이 발견되면 제한적으로 참여한다.

## 작업별 역할 운영

AI-DLC 단계별 책임자가 해당 산출물의 실행 주도를 맡고, 다른 핵심 역할은 탐색자 또는 검토자로 참여한다.

| 작업 상황 | 실행 주도 | 주 탐색자 | 추가 탐색자 |
|---|---|---|---|
| 범위·우선순위 구체화 | 전달 | 제품 책임자 | 아키텍처, 품질 |
| 실행 경계·계약 설계 | 아키텍처 | 개발 | 보안, 품질 |
| 조회 능력 구현 | 개발 | 아키텍처 | 품질, 보안 |
| 등록 능력 구현 | 개발 | 품질 | 보안, 아키텍처 |
| 수정 능력 구현 | 개발 | 아키텍처 | 품질, 보안 |
| 통합·회귀·보안 검증 | 품질 | 개발 | 보안, 전달 |
| 사용자 가치 확인과 완료 판단 | 제품 책임자 | 전달 | 품질 |

## 협업 리듬

- 저장소의 승인된 산출물을 단일 기준으로 삼아 비동기적으로 진행한다.
- 질문, 종합 요약, 단계 완료 시 요청자에게 결정을 요청한다.
- 한 번에 하나의 주요 능력 흐름에 집중하며, 공통 안전 경계 뒤에 조회, 등록, 수정, 통합 검증 순으로 진행한다.
- 각 역할은 자신의 전문 관점만 별도로 넘기지 않고 현재 작업의 완료 기준에 직접 반영한다.
- 중요한 계약·보안·품질 판단은 근거와 함께 산출물 및 테스트에 남긴다.
- 상충되는 의견은 전달 책임자가 쟁점을 정리하고 제품 범위는 요청자, 계약은 아키텍처와 ITSM 운영, 보안 판정은 보안 역할이 각각 책임진다.

## 의사소통과 에스컬레이션

| 상황 | 우선 행동 | 결정 주체 |
|---|---|---|
| 범위 또는 사용자 동작이 불명확함 | 선택지와 영향을 정리해 질문 | 요청자 / 제품 책임자 |
| ITSM 계약 의미가 불명확함 | 두 계약 문서의 근거를 대조하고 내부 자문 요청 | 아키텍처, 필요 시 ITSM 운영 |
| 비밀정보·권한 위험이 발견됨 | 해당 흐름을 완료 처리하지 않고 완화안 제시 | 보안 책임자, 범위 영향은 요청자 |
| 회귀 또는 테스트 실패가 발생함 | 재현 조건과 영향 범위를 기록하고 수정 | 품질·개발 |
| 범위 밖 기능이나 신규 인프라가 필요함 | 현재 범위에 추가하지 않고 변경 영향 제시 | 요청자 / 제품 책임자 |

## 완료 정의와 공동 점검

각 주요 능력은 다음 공동 점검을 통과해야 한다.

- 개발 역할: 승인된 업무 동작이 구현되고 허용 범위를 벗어나지 않는다.
- 아키텍처 역할: 기존 구조와 계약 경계가 유지되고 숨은 의존성이 없다.
- 보안 역할: 위임 권한과 비밀정보 비노출 조건이 증거로 확인된다.
- 품질 역할: 실제 OpenAI API 없이 주요 성공·실패·회귀 흐름을 재현할 수 있다.
- 전달 역할: 의존성과 완료 증거가 사용자 가치 및 백로그 능력에 연결된다.
- 요청자: 단계 산출물과 범위 결과를 검토하고 승인한다.

## 협업 시작 체크리스트

- [ ] 요청자와 역할 팀이 범위 내·외 및 정확히 세 도구 원칙을 확인한다.
- [ ] 공통 안전 경계를 첫 작업 흐름으로 합의한다.
- [ ] 역할별 주도·지원·자문 책임을 확인한다.
- [ ] 질문·요약·단계 완료 승인 방식과 비동기 협업 방식을 확인한다.
- [ ] ITSM 운영·보안 내부 자문의 호출 조건을 확인한다.
- [ ] 기존 테스트 기준선과 신규 테스트의 실제 OpenAI 비호출 원칙을 확인한다.
- [ ] 등록 중복과 수정 충돌을 완료 전 필수 검증 항목으로 확인한다.
- [ ] 상시 외부 인력이나 신규 팀이 필요하지 않음을 확인한다.

## 구성 결론

단일 교차기능 팀이 전체 기능을 소유하고, 요청자가 제품 책임자와 승인자로 참여하는 구성이 가장 적합하다. 이 구성은 역할 간 인수인계를 줄이고 비밀정보·권한·중복·충돌·회귀 위험을 각 능력의 진행 중에 함께 다루며, 필요한 경우에만 내부 ITSM 운영 또는 보안 자문을 추가한다.
