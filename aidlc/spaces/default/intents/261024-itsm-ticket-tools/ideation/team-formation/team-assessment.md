# ITSM 티켓 도구 팀 평가

## 평가 근거

이 평가는 승인된 `scope-document.md`의 범위·수용 경계, `intent-backlog.md`의 능력 순서와 의존성, `feasibility-assessment.md`의 기술·보안 위험을 팀 운영 관점으로 변환한다. 팀 구성 결정은 `team-formation-questions.md`의 승인된 답변을 따른다.

## 권고 팀 형태

하나의 스트림 정렬형 교차기능 팀이 기능 전체를 소유한다. AI-DLC 역할 팀이 분석·설계·구현·검증을 수행하고, 요청자는 제품 책임자이자 단계 승인자로 참여한다. 새 서비스나 새 화면이 없는 단일 기능 확장이므로 여러 팀으로 분리하지 않는다.

### 핵심 참여 역할

| 역할 | 주된 책임 | 참여 수준 |
|---|---|---|
| 요청자 / 제품 책임자 | 범위·우선순위·사용자 가치 결정, 단계별 최종 승인 | 모든 중요 결정과 승인 지점 |
| 전달 책임자 | 작업 흐름 조율, 의존성·위험·완료 기준 관리 | 전 과정 |
| 아키텍처 책임자 | 기존 구조 보존, 실행 경계와 계약 일관성 검토 | 설계 및 주요 변경 검토 |
| 개발 책임자 | 기존 프로젝트 확장과 자동화 테스트 구현 | 구현 중심 전 과정 |
| 보안·DevSecOps 책임자 | 위임 권한, 비밀정보 비노출, 안전한 오류와 보안 검증 | 보안 결정 및 검증 |
| 품질 책임자 | 계약·통합·회귀 테스트 전략과 증거 확인 | 요구 구체화부터 완료 검증 |
| ITSM 운영 책임자 | 계약 또는 운영 의미가 불명확할 때 자문 | 필요 시 Consulted |

UX 재설계, 신규 인프라, 별도 클라우드 구성은 범위 밖이므로 디자인·클라우드·운영·배포 전문 역할은 상시 팀에 두지 않고 해당 단계에서 실제 필요가 확인될 때만 자문한다.

## 가용성과 수용 능력 평가

- 고정 납기, 추가 예산, 변경 동결 또는 경쟁 우선순위로 인한 인력 제약은 확인되지 않았다.
- 정량적인 사람별 FTE나 근무 시간은 제공되지 않았으므로 임의의 수치를 만들지 않는다.
- 저장소 산출물을 중심으로 비동기 진행하고 질문, 요약 확인, 단계 완료 시 요청자가 응답하는 것을 기본 가용성 계약으로 삼는다.
- 팀의 진행 중 작업 한도는 하나의 주요 능력 흐름으로 둔다. 공통 안전 경계가 확정되기 전에 조회·등록·수정을 각각 독립 추진하지 않는다.
- ITSM 계약 또는 보안 해석이 막힐 때만 내부 ITSM 운영·보안 책임자에게 자문하며, 외부 계약자나 전문 서비스는 계획하지 않는다.

## 수용 능력 배분 합의

작업량은 고정 인원 비율이 아니라 능력 흐름과 위험에 따라 배분한다.

| 순서 | 작업 흐름 | 주도 역할 | 필수 동반 역할 | 완료 조건 |
|---:|---|---|---|---|
| 1 | 공통 안전 실행 경계 | 아키텍처 | 개발, 보안, 품질 | 권한·가시성·비밀 보호·오류 경계 합의 |
| 2 | 조회 능력 | 개발 | 품질, 아키텍처 | 목록·검색·상세와 권한 비노출 검증 가능 |
| 3 | 등록 능력 | 개발 | 보안, 품질 | 명시적 확인과 중복 방지 검증 가능 |
| 4 | 수정 능력 | 개발 | 아키텍처, 보안, 품질 | 허용 변경과 충돌 보호 검증 가능 |
| 5 | 통합 검증과 안내 | 품질 | 개발, 보안, 전달 | 전체 테스트·회귀·성과·README 증거 완료 |

요청자 승인 대기 중에는 승인 없이 다음 의사결정을 확정하지 않는다. 다만 이미 승인된 범위에 대한 분석과 검증 준비는 비동기적으로 진행할 수 있다.

## RACI 매트릭스

R은 수행, A는 최종 책임·승인, C는 자문, I는 공유를 뜻한다.

| 활동 | 요청자 / 제품 | 전달 | 아키텍처 | 개발 | 보안 | 품질 | ITSM 운영 |
|---|---|---|---|---|---|---|---|
| 범위·우선순위 결정 | A | R | C | C | C | C | I |
| ITSM 계약 해석 | I | C | A | R | C | C | C |
| 권한·비밀정보 경계 | I | C | R | R | A | C | C |
| 기능 구현 | I | C | C | A/R | C | C | I |
| 테스트 전략과 회귀 검증 | I | C | C | R | C | A/R | I |
| 보안 결과 판정 | I | C | C | R | A/R | C | C |
| 사용자 가치 확인 | A | R | I | C | I | R | I |
| 단계 완료 승인 | A/R | I | I | I | I | I | I |

## 의존성과 에스컬레이션

- 제품 범위나 우선순위가 바뀌면 요청자가 결정한다.
- `docs/itsm/integration-guide.md`와 `docs/itsm/openapi.json` 사이에 해석 충돌이 발견되면 아키텍처 책임자가 정리하고 ITSM 운영 책임자에게 자문한다.
- 위임 토큰, 권한 또는 비밀정보 노출 가능성이 발견되면 보안 책임자가 완료를 보류하고 요청자에게 영향과 선택지를 제시한다.
- 기존 동작 회귀나 자동화 테스트 실패가 있으면 품질 책임자가 완료를 보류하고 개발 책임자와 수정 범위를 확정한다.
- 범위 밖 기능이나 신규 인프라가 필요해지면 현재 작업에 암묵적으로 추가하지 않고 요청자의 범위 결정을 받는다.

## 팀 평가 결론

현재 역할 구성은 `intent-backlog.md`의 다섯 능력을 수행하기에 충분하다. 확인된 상시 역량 공백은 없으며, 가장 중요한 운영 조건은 개발·아키텍처·보안·품질을 마지막에 순차 검토하는 대신 하나의 흐름에서 함께 적용하는 것이다. 추가 인력보다 계약 해석이 필요한 순간에 정확한 내부 자문을 호출하는 방식이 범위와 인지 부하에 적합하다.
