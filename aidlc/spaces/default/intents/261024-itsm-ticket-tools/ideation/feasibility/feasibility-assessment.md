# ITSM 티켓 도구 타당성 평가

## 결론

이번 기능은 **조건부로 실현 가능하며 진행을 권고한다**. 기존 Python/FastAPI 애플리케이션에는 OpenAI Agents SDK의 `Agent`, `Runner`, SDK 세션, 서버 측 사용자 세션, ITSM 사용자 위임 토큰 발급·갱신, `httpx` 기반 ITSM 클라이언트와 네트워크 없는 테스트 기반이 이미 있다. 따라서 새 에이전트나 별도 서비스를 만들지 않고 현재 구조를 확장해 `ticket_read`, `ticket_write`, `ticket_update` 세 도구를 연결할 수 있다.

핵심 조건은 ITSM 호출 기능과 위임 토큰을 서버 측 실행 context로만 전달하고, 모델에 공개되는 도구 인자·결과·지침에는 토큰이나 자격증명을 포함하지 않는 것이다. 수정은 ITSM API의 낙관적 잠금 요구사항에 따라 현재 `version`을 확인하고 `If-Match`를 보내야 한다.

## 평가 입력과 추적성

- 기능 목적, 성공 기준, 제외 범위: `ideation/intent-capture/intent-statement.md`
- 인증·권한·가시성·오류·페이지네이션·낙관적 잠금: `docs/itsm/integration-guide.md`
- 엔드포인트와 입력·응답 스키마: `docs/itsm/openapi.json`
- 현재 구현: `app/agent/assistant.py`, `app/agent/service.py`, `app/agent/context.py`, `app/itsm_auth.py`, `app/session.py`, `app/main.py`
- 현재 테스트: `tests/test_agent.py`, `tests/test_session.py`, `tests/conftest.py`
- 제약 결정과 승인된 요약: `ideation/feasibility/feasibility-questions.md`
- 검토 지적: `ideation/intent-capture/reviews/review-01.md`부터 `review-04.md`

## 검토 지적 반영 확인

| 지적 | 요구된 조치 | 반영 결과 |
|---|---|---|
| R-01 | 사용자 가치와 직접 연결된 측정 가능한 결과 추가 또는 미측정 결정 | 조회·등록·수정 시나리오의 외부 화면 전환 0회와 완료 시간 감소를 성공 기준에 포함 |
| R-02 | 근거 없는 “조작 단계 1단계 감소”를 확인하거나 교체 | 해당 임계값과 단계 수 측정을 제거 |
| R-03 | 근거 없는 “정량 임계값 유보”를 확인하거나 제거 | 해당 유보 결정을 제거하고 확인된 측정 기준만 유지 |
| R-04 | 시간 단축을 방향성 목표로 수용하거나 측정 기준 추가 | 동일 조건에서 각 시나리오를 양 방식으로 3회 수행하고 Assistant의 시나리오별 중앙 완료 시간이 더 짧아야 한다는 기준 추가 |

1~4차 검토의 고유 지적은 R-01부터 R-04까지이며 모두 반영됐다. 조치 결과는 `intent-statement.md`의 `Review Finding Resolution`에도 추적된다.

## 기술적 실현 가능성

| 영역 | 현재 상태 | 필요한 확장 | 평가 |
|---|---|---|---|
| Agent 도구 연결 | `TOOLS`가 비어 있고 `build_agent()`가 목록을 Agent에 전달 | SDK `function_tool`로 세 도구를 만들고 `TOOLS`에 정확히 세 개만 등록 | 높음 |
| 사용자 실행 주체 | `CurrentUser`는 서버 세션에서 복원되고 `AgentUserContext`는 검증된 사용자 정보만 보유 | 도구용 ITSM 호출 capability를 서버 측 context에 추가하되 비밀값은 repr·로그·모델 입력에서 제외 | 높음, 보안 설계 필요 |
| 위임 토큰 | 로그인 시 발급하고 만료 전 갱신하는 `itsm_token_for()`가 존재 | Agent 실행 전 또는 도구 호출 시 유효 토큰을 확보해 기존 클라이언트에 전달 | 높음 |
| ITSM HTTP | 인증·디렉터리용 `ItsmAuthClient`와 공통 오류 처리 존재 | 동일 클라이언트에 티켓 GET/POST/PATCH 추가 | 높음 |
| `ticket_read` | 미구현 | `ticket_id`가 있으면 상세 GET, 없으면 필터·커서 기반 목록 GET | 높음 |
| `ticket_write` | 미구현 | 계약상 필수 등록 필드와 선택 필드만 POST하고 멱등키 사용 | 높음 |
| `ticket_update` | 미구현 | 허용 필드만 PATCH하고 상세 조회에서 얻은 `version`을 `If-Match`에 사용 | 중간—동시 수정 충돌 처리 필요 |
| 권한·가시성 | ITSM API가 위임 토큰 기준으로 판정 | 로컬에서 권한을 확대하지 않고 403/404 등 계약 오류를 안전하게 전달 | 높음 |
| 테스트 | FakeModel과 `httpx.MockTransport`가 존재 | Fake ITSM에 티켓 계약 동작을 추가하고 도구·Agent 통합·회귀 테스트 작성 | 높음 |
| 운영 구조 | 단일 기존 앱과 설정·배포 구조 | 새 서비스·새 인프라 없이 앱 내부 모듈만 확장 | 높음 |

## 계약 적합성 분석

### 조회

- 목록·검색은 `GET /api/v2/tickets`, 상세는 `GET /api/v2/tickets/{id}`로 충족된다.
- 목록은 기본 20, 최대 100의 커서 페이지네이션이며 같은 조건에서만 `next_cursor`를 재사용한다.
- 검색어, 상태, 우선순위, 서비스, 컴포넌트, 모델, 담당자, 요청자, 분류, 주요 장애 여부와 생성·수정 시각 필터를 계약 범위 안에서 지원할 수 있다.
- 보이지 않는 티켓의 404는 실제 부재와 구분하지 않는다. 도구도 이 정보 비노출 계약을 유지해야 한다.

### 등록

- 필수 입력은 `title`, `description`, `service_id`, `impact_level`, `urgency`, `impact_note`, 시간대가 포함된 `occurred_at`이다.
- `component_id`, `model`, `classification`은 선택 입력이다.
- ID, 요청자, 상태, 우선순위, 담당 그룹과 서버 관리 시각은 서버가 결정하므로 도구 입력과 POST 본문에서 제외한다.
- 재시도 중 중복 등록을 막도록 요청 단위 멱등키를 사용하며 키에는 사용자나 비밀정보를 넣지 않는다.

### 수정

- 허용 필드는 `title`, `description`, `component_id`, `model`, `impact_level`, `urgency`, `impact_note`, `is_major`이다.
- 사용자 요청의 “영향 범위”는 계약 필드 `impact_note`에 대응한다.
- 빈 수정은 422가 되므로 최소 한 필드가 필요하다.
- 도구가 먼저 현재 상세를 읽어 `version`을 얻고 `If-Match`와 함께 PATCH한다. 그 사이 다른 변경으로 412가 발생하면 최신 값을 덮어쓰지 않고 충돌을 알린다.
- `is_major`는 별도 권한이 필요한 계약 필드이므로 API의 권한 판정을 그대로 따른다.

## 실행 경계

1. FastAPI 라우트가 서버 세션에서 현재 사용자를 확인하고 유효한 위임 토큰을 확보한다.
2. `Runner.run()`에는 기존 대화 세션과 서버가 만든 도구 실행 context를 전달한다.
3. 모델은 세 도구의 업무 인자만 선택하며 토큰·클라이언트 secret·OpenAI API key를 보거나 생성하지 않는다.
4. 도구는 기존 ITSM HTTP 클라이언트로 API v2를 호출한다.
5. 도구 결과는 업무 데이터 또는 정제된 계약 오류만 모델에 반환한다.

이 경계는 `intent-statement.md`의 현재 Assistant 내 처리, 기존 사용자 권한 유지, 비밀정보 비노출, 기존 동작 무회귀 성공 기준을 직접 지원한다.

## 보안·컴플라이언스 평가

- 권한과 행 단위 가시성은 위임 토큰을 받은 ITSM API가 최종 판정한다. 로컬 권한 목록은 승인 근거로 사용하지 않는다.
- bearer 토큰, 클라이언트 secret, OpenAI API key는 function tool 스키마, Agent 지침, 사용자 메시지, 도구 결과에 포함하지 않는다.
- `repr=False`만으로 충분하지 않으므로 예외·요청 객체·헤더·상류 응답을 문자열화하지 않는 안전한 오류 매핑과 비밀값 검출 테스트를 둔다.
- ITSM 오류는 안정적인 `code`, HTTP 상태, 안전한 설명과 `request_id`만 선별한다. 원본 헤더나 전체 예외 객체는 반환하지 않는다.
- 별도 규제는 식별되지 않았고 기존 사내 보안 정책을 적용한다. 티켓 본문에는 업무상 민감정보가 있을 수 있으므로 API 가시성 범위를 우회하거나 목록 전체를 과다 반환하지 않는다.
- 개발 문서와 기존 설정의 개발 자격증명은 런타임 Agent 입력과 결과에 복사하지 않고, 운영 자격증명은 기존 환경 설정 경로를 사용한다.

## 운영 및 품질 평가

- 별도 처리량·가용성 목표는 두지 않고 기존 Assistant 기준을 유지한다.
- ITSM의 분당 300회 제한, 429 `Retry-After`, 10초 HTTP 시간 제한을 존중한다. 읽기 재시도는 제한적으로 고려하고, 쓰기는 멱등성 또는 명확한 실패 상태가 보장될 때만 재시도한다.
- 기존 모델명과 reasoning 설정, 사용자 전환, 대화 이력, 화면/API 계약은 변경 대상이 아니다.
- 신규 자동화 테스트는 FakeModel과 `httpx.MockTransport`로 도구 선택·실행 및 ITSM 요청을 검증하며 실제 OpenAI API를 호출하지 않는다.
- 기준선 검증 결과: `.venv/bin/pytest -q`에서 기존 테스트 37개 통과.
- 사용자 성과 검증은 동일 입력 조건의 대표 조회·등록·수정 시나리오를 기존 화면 방식과 Assistant 방식에서 각각 3회 수행하고 시나리오별 중앙 완료 시간을 비교한다.

## 주요 위험과 완화

| 위험 | 영향 | 완화 |
|---|---|---|
| 서버 측 토큰이 모델 입력이나 오류에 섞임 | 매우 높음 | 모델과 분리된 context/capability, 안전한 오류 DTO, 비밀값 부재 테스트 |
| 수정 직전 다른 사용자가 티켓을 변경 | 높음 | 상세 조회 후 `If-Match`, 412에서 덮어쓰기 금지 및 재조회 안내 |
| 등록 재시도로 중복 티켓 생성 | 높음 | 요청 단위 멱등키와 재사용 규칙 테스트 |
| 권한 없는 티켓 존재 여부 노출 | 높음 | ITSM의 404 의미 유지, 추측성 설명 금지 |
| API 장애·만료·429로 Agent 실행 실패 | 중간 | 토큰 갱신, 시간 제한, 계약별 안전한 오류 안내, 쓰기 무조건 재시도 금지 |
| 넓은 도구 스키마로 잘못된 필드 전달 | 중간 | OpenAPI 기반 enum·길이·선택 필드 제한, 추가 필드 금지, 계약 테스트 |

## 진행 조건

- Agent에 노출되는 티켓 도구는 정확히 세 개로 유지한다.
- 기존 서버 세션에서 유효한 사용자 위임 토큰을 얻는 경로를 재사용한다.
- 모든 HTTP 요청은 ITSM API v2 계약에 한정한다.
- 쓰기·수정 입력은 OpenAPI 허용 필드만 전송하고 수정에는 낙관적 잠금을 적용한다.
- 비밀값 비노출 테스트와 실제 OpenAI 호출 없는 자동화 테스트를 통과한다.
- 기존 37개 테스트와 신규 테스트가 함께 통과하고 README를 갱신한다.
- 대표 시나리오의 외부 화면 전환 0회와 기존 방식 대비 중앙 완료 시간 감소를 확인한다.

## 권고

위 진행 조건을 설계·인수 기준으로 고정하고 다음 단계로 진행한다. 현재 확인된 차단 이슈는 없으며 신규 인프라·외부 서비스·AWS 변경도 필요하지 않다.
