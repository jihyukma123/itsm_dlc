# ITSM 티켓 대화 사용자 흐름

## 흐름 원칙과 근거

이 흐름은 `intent-statement.md`의 외부 ITSM 화면 전환 0회 목표, `scope-document.md`의 기존 화면 유지와 명시적 확인 원칙, `intent-backlog.md`의 IB-01부터 IB-04까지의 사용자 능력을 반영한다.

- 진입점은 기존 Assistant 대화 입력창 하나다.
- 조회는 데이터 변경이 없으므로 결과를 바로 안내한다.
- 등록·수정은 최종 요약과 명시적 확인 전에는 실행하지 않는다.
- 사용자 취소, 정보 수정, 오류 복구가 모두 대화 흐름 안에 있어야 한다.
- ITSM이 판정한 권한과 가시성을 바꾸거나 설명으로 추측하지 않는다.

## 전체 흐름

```text
[USER_NATURAL_LANGUAGE_REQUEST]
        |
        v
[ASSISTANT_CLARIFIES_INTENT_AND_REQUIRED_INFORMATION]
        |
        +---- READ ----> [ITSM_DECISION] ----> [LIST_OR_DETAIL]
        |
        +---- CREATE ----> [COLLECT_REQUIRED_INFORMATION] ----> [REVIEW_AND_CONFIRM]
        |                                      |
        |                                      +---- CONFIRM ----> [ITSM_ACTION]
        |                                      +---- EDIT -------> [UPDATE_REVIEW]
        |                                      +---- CANCEL -----> [NO_ACTION]
        |
        +---- UPDATE ----> [READ_CURRENT_TICKET] ----> [COLLECT_CHANGES]
                                               |
                                               v
                                      [REVIEW_AND_CONFIRM]
                                               |
                                               +---- CONFIRM ----> [ITSM_ACTION]
                                               +---- EDIT -------> [UPDATE_REVIEW]
                                               +---- CANCEL -----> [NO_ACTION]
```

텍스트 대체: 사용자는 기존 대화 입력창에서 요청한다. 조회는 권한 범위의 결과로 끝나고, 등록·수정은 필요한 정보 수집 뒤 요약을 확인해야만 ITSM 처리로 넘어간다. 수정 또는 취소를 선택하면 실행하지 않는다.

## 흐름 1 — 티켓 검색과 목록

- **사용자:** 일반 사내 사용자 또는 서비스 데스크 담당자
- **시작:** 기존 대화 입력창에서 검색 조건을 자연어로 요청
- **주요 단계:**
  - Assistant가 검색 의도와 모호한 조건을 확인한다.
  - 현재 사용자의 권한과 가시성 범위에서 ITSM이 결과를 판정한다.
  - Assistant가 핵심 정보만 간결한 목록으로 안내한다.
  - 다음 결과가 있으면 사용자에게 다음 페이지를 요청할 수 있다고 알린다.
  - 사용자가 상세 조회, 다음 결과, 조건 변경 또는 종료를 선택한다.
- **성공 결과:** 사용자가 외부 화면으로 이동하지 않고 원하는 티켓을 식별한다.
- **예외 흐름:**
  - 결과 없음 -> 조건 변경 또는 새 검색 안내
  - 잘못된 조건 -> 어떤 값을 고쳐야 하는지 안내
  - 호출 제한 또는 일시 장애 -> 안전한 재시도 시점이나 다음 행동 안내
  - 보이지 않는 티켓 -> 존재 또는 권한 여부를 구분해 추측하지 않음

## 흐름 2 — 티켓 상세 조회

- **시작:** 사용자가 티켓 ID 또는 목록의 한 항목을 상세히 요청
- **주요 단계:**
  - ITSM이 현재 사용자에게 해당 티켓이 보이는지 판정한다.
  - Assistant가 허용된 상세 정보를 의미 있는 항목별로 안내한다.
  - 선택 정보가 없으면 값을 추측하지 않고 없는 상태로 표시한다.
  - 사용자는 종료하거나 허용된 내용의 수정을 요청할 수 있다.
- **성공 결과:** 사용자가 대화에서 필요한 티켓 상세를 확인한다.
- **예외 흐름:** 찾을 수 없거나 보이지 않음 -> 두 경우를 구분하지 않는 안전한 안내

## 흐름 3 — 티켓 등록

- **시작:** 사용자가 새 티켓 등록 의사를 말한다.
- **주요 단계:**
  - Assistant가 제목, 설명, 서비스, 영향도, 긴급도, 영향 범위, 발생 시각 등 필수 정보를 확인한다.
  - 빠진 정보가 있으면 해당 정보만 추가로 질문한다.
  - 실행 직전 모든 등록 내용을 한 번에 요약한다.
  - 사용자에게 확인·수정·취소 중 하나를 명확히 요청한다.
  - **확인:** ITSM이 현재 사용자 권한으로 처리하고 결과를 반환한다.
  - **수정:** 사용자가 말한 항목을 바꾸고 전체 요약을 다시 보여준다.
  - **취소:** 티켓을 만들지 않고 취소를 알린다.
- **성공 결과:** 새 티켓의 안전한 식별 정보와 등록 완료를 안내한다.
- **예외 흐름:**
  - 입력 오류 -> 잘못된 항목과 수정 방법 안내
  - 권한 거부 -> 권한을 추측하지 않고 수행할 수 없음을 안내
  - 세션 또는 위임 인증 만료 -> ITSM 요청과 등록이 실행되지 않았음을 알리고 재로그인 뒤 다시 요청하도록 안내
  - 결과가 불명확한 장애 -> 성공을 추측하지 않고 원래 중복 방지 상태를 유지한 채 기존 결과 확인 또는 안전한 동일 요청 재시도만 제공
  - 동일 등록 요청 재전송 -> 원래 중복 방지 상태를 재사용해 기존 결과 또는 하나의 등록 결과만 반환

## 흐름 4 — 티켓 수정

- **시작:** 사용자가 대상 티켓과 변경 내용을 말한다.
- **주요 단계:**
  - Assistant가 현재 티켓을 확인하고 사용자에게 보이는 최신 값을 기준으로 삼는다.
  - 허용된 변경인지 확인하고, 바뀌는 항목만 이전 값과 새 값으로 요약한다.
  - 사용자에게 확인·수정·취소 중 하나를 명확히 요청한다.
  - **확인:** 최신 상태가 유지된 경우에만 ITSM이 변경을 적용한다.
  - **수정:** 변경 요청을 고치고 전체 변경 요약을 다시 보여준다.
  - **취소:** 변경하지 않고 취소를 알린다.
- **성공 결과:** 변경된 항목과 수정 완료를 안전하게 안내한다.
- **예외 흐름:**
  - 허용되지 않은 필드 -> 지원되는 변경 범위를 안내
  - 변경할 내용 없음 -> 실행하지 않고 알려줌
  - 동시 수정 충돌 -> 덮어쓰지 않고 최신 상세 재확인 안내
  - 티켓 미발견 또는 비가시성 -> 두 경우를 구분해 추측하지 않음

## 흐름 5 — 오류 복구

| 상황 | 사용자에게 보이는 안내 | 다음 행동 |
|---|---|---|
| 필수 정보 부족 | 빠진 업무 정보 | 필요한 값 제공 |
| 잘못된 입력 | 수정해야 할 항목과 허용 형태 | 값 수정 |
| 티켓 미발견 또는 비가시성 | 티켓을 확인할 수 없다는 안전한 설명 | ID 확인 또는 다른 검색 |
| 권한 거부 | 현재 요청을 수행할 수 없다는 설명 | 필요 시 내부 절차 확인 |
| 호출 제한 | 잠시 후 다시 시도해야 한다는 설명 | 안내된 시점 이후 재시도 |
| 일시적 장애 | 현재 완료하지 못했다는 설명 | 안전한 작업만 재시도 |
| 서버 세션 또는 위임 인증 만료 | 로그인이 만료되었고 요청을 보내지 않아 등록·수정이 실행되지 않았다는 설명 | 다시 로그인한 뒤 사용자가 같은 요청을 다시 입력 |
| 수정 충돌 | 최신 변경을 덮어쓰지 않았다는 설명 | 최신 상세 조회 후 재요청 |
| 등록 결과 불명확 | 성공·실패를 추측하지 않으며 원래 요청의 중복 방지 상태가 유지된다는 설명 | 기존 처리 결과 확인 또는 원래 상태를 재사용한 안전한 동일 요청 재시도 |
| 동일 등록 요청 재전송 | 새 등록을 시작하지 않고 기존 결과 또는 하나의 등록 결과만 반환한다는 설명 | 반환된 결과 확인; 여전히 불명확하면 새 요청을 만들지 않고 대기 또는 추가 확인 |

오류 안내에는 원본 오류 본문, 비밀정보, 내부 예외, 요청 헤더 또는 권한 추측을 포함하지 않는다.

## 흐름 6 — 인증 만료와 변경 작업 복구

```text
[CREATE_OR_UPDATE_CONFIRMED]
        |
        v
[CHECK_SERVER_SESSION_AND_DELEGATED_AUTH]
        |
        +---- VALID ------> [SEND_ITSM_REQUEST]
        |
        +---- EXPIRED ----> [DO_NOT_SEND_REQUEST]
                              |
                              v
                    [ANNOUNCE_NO_CHANGE_APPLIED]
                              |
                              v
                    [SIGN_IN_AGAIN_AND_USER_RETRIES]
```

텍스트 대체: 등록 또는 수정 확인 뒤 서버 세션과 사용자 위임 인증을 확인한다. 유효할 때만 ITSM 요청을 보내며, 만료됐으면 요청을 보내지 않고 변경이 실행되지 않았음을 알린다. 사용자가 다시 로그인한 뒤 직접 같은 요청을 다시 입력한다.

- 재로그인 전 자동 재시도는 하지 않는다.
- 인증 오류 원문, 토큰 값, client secret 또는 내부 식별자는 사용자 메시지에 포함하지 않는다.
- 재로그인 뒤에는 현재 사용자 세션과 새 위임 인증으로 요청을 다시 평가하며, 이전 사용자의 권한이나 결과를 재사용하지 않는다.

## 흐름 7 — 등록 결과 불명확과 중복 방지

```text
[CONFIRMED_CREATE_SENT_WITH_IDEMPOTENCY_STATE]
        |
        v
[RESPONSE_LOST_OR_TIMEOUT]
        |
        v
[RESULT_NOT_CONFIRMED_AND_NO_ASSUMPTION]
        |
        +---- CHECK_RESULT_AVAILABLE ----> [RETURN_EXISTING_RESULT]
        |
        +---- SAME_REQUEST_RETRY --------> [REUSE_ORIGINAL_IDEMPOTENCY_STATE]
        |                                      |
        |                                      v
        |                             [RETURN_ONE_CREATE_OUTCOME]
        |
        +---- STILL_UNRESOLVED -------> [NO_NEW_CREATE_REQUEST]
                                               |
                                               v
                                  [WAIT_OR_ADDITIONAL_CONFIRMATION]
```

텍스트 대체: 확인된 등록 요청의 응답이 사라지면 성공 여부를 추측하지 않는다. 기존 결과를 확인하거나 동일 요청의 원래 중복 방지 상태로만 안전하게 재시도한다. 그래도 불명확하면 새 등록을 만들지 않고 대기 또는 추가 확인을 안내한다.

- 같은 등록 내용의 재전송은 원래 중복 방지 상태를 재사용한다.
- 기존 결과가 확인되면 새 등록 없이 그 결과를 반환한다.
- 사용자가 등록 내용을 바꾸면 새 의도로 보고 전체 요약과 명시적 확인을 다시 받는다.
- 새 중복 방지 상태로 조용히 재시도하거나 여러 티켓을 만들 가능성이 있는 자동 반복은 금지한다.

## 사용자와 시스템의 개념적 상호작용

```text
[USER]
   |
   v
[EXISTING_ITSM_ASSISTANT_CONVERSATION]
   |
   v
[UNDERSTAND_AND_CONFIRM_REQUEST]
   |
   v
[EXISTING_ITSM_AUTHORIZATION_AND_VISIBILITY_DECISION]
   |
   v
[BUSINESS_RESULT_OR_SAFE_ERROR]
   |
   v
[TEXT_RESPONSE_IN_EXISTING_CONVERSATION]
```

텍스트 대체: 사용자의 요청은 기존 Assistant 대화를 통해 처리되며, 기존 ITSM의 권한과 가시성 판단 결과만 안전한 업무 응답으로 돌아온다.

## 접근성 및 기기 원칙

- 기존 화면의 반응형 동작과 지원 기기 범위를 바꾸지 않는다.
- 기존 페이지 `h1`과 `header`·`main`·대화 입력 `form` landmark를 유지한다. 업무 상태 메시지는 `h2`, 메시지 안의 하위 결과 묶음은 `h3`로 구성한다.
- 모든 진행, 빈 결과, 성공, 오류, 충돌, 확인 상태를 텍스트로 명시한다.
- 색상, 아이콘, 위치, 움직임만으로 의미를 전달하지 않는다.
- 대화의 시각적 순서와 화면 읽기 순서를 일치시킨다.
- 사용자는 기존 대화 입력창까지 키보드로 이동하고 모든 선택을 텍스트로 입력할 수 있다. 새 메시지가 추가되어도 초점은 입력창에 유지한다.
- 일반 진행·결과·확인은 `role="status"`의 polite live 알림으로, 인증 만료·충돌·실패·등록 결과 불명확은 `role="alert"`로 메시지와 다음 행동을 한 번 전달한다.
- 목록 항목과 상세 필드는 식별 가능한 텍스트 레이블을 가진다.
- 긴 결과는 한 번에 과도하게 표시하지 않고 다음 결과 또는 상세 요청으로 점진적으로 공개한다.

## 성공 흐름 점검

- 조회·등록·수정 모두 기존 대화 화면 밖으로 이동하지 않는다.
- 등록·수정은 명시적 확인 전에는 실행되지 않는다.
- 사용자는 확인 전 내용을 수정하거나 취소할 수 있다.
- 세션 또는 위임 인증이 만료되면 등록·수정 요청을 보내지 않고 미실행 사실과 재로그인 후 재요청 방법을 알린다.
- 등록 결과가 불명확하거나 같은 요청이 재전송돼도 원래 중복 방지 상태를 유지해 티켓이 중복 생성되지 않는다.
- 권한과 가시성 결과를 Assistant가 확대하거나 추측하지 않는다.
- 오류가 사용자의 다음 행동을 제공하면서도 비밀정보와 내부 정보를 노출하지 않는다.
- 기존 화면, 사용자 전환, 세션, 대화 이력의 사용 방식은 바뀌지 않는다.
