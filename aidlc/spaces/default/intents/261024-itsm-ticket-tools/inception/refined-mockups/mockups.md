## Design Boundary

이 명세는 기존 ITSM Assistant의 한 화면, 사용자 선택기, 대화 로그, 대화 입력창을 그대로 사용한다. 새 화면·탭·버튼·카드·메뉴·모달을 추가하지 않으며, ITSM 업무 상태는 기존 `.msg.assistant` 또는 `.msg.error` 메시지 안의 텍스트 구조로 표현한다.

- 사용자는 외부 ITSM 화면으로 이동하지 않는다.
- 등록·수정은 명시적 확인 전에는 실행하지 않는다.
- 목록·상세·업무 오류에 포함된 ITSM 텍스트는 데이터로만 표시한다.
- 티켓 ID는 실제 값이나 샘플을 문서에 넣지 않고 `[티켓 ID]` 자리표시자로 표현한다.
- 기존 `820px` 최대 폭, 유동 너비, topbar 줄바꿈, 입력창·전송 버튼 배치를 상속한다.

## Base Conversation Frame

```text
┌──────────────────────────────────────────────────────────────┐
│ ITSM Assistant                     사용자 [현재 사용자 ▾]   │
├──────────────────────────────────────────────────────────────┤
│ 대화                                      대화 초기화        │
│                                                              │
│ [사용자 메시지]                                              │
│                                  [Assistant 업무 메시지]      │
│                                                              │
│ [기존 대화 입력창.............................] [전송]        │
└──────────────────────────────────────────────────────────────┘
```

텍스트 대체: 현재 화면의 header, 사용자 선택기, 단일 대화 패널, 대화 로그, textarea와 전송 버튼을 유지한다. 티켓 기능은 Assistant 메시지 내용만 확장한다.

## Message Anatomy

업무 메시지는 사용자가 위에서 아래로 스캔할 수 있도록 다음 순서를 유지한다. 기존 대화 영역의 `h2`인 “대화” 아래에서 각 Assistant 업무 메시지의 상태 제목은 `h3`로 표현한다. 필드 묶음은 추가 heading을 반복하지 않고 레이블이 있는 목록 또는 설명 목록으로 구성한다. 이 계층은 Rough Mockups의 메시지별 `h2`·그룹별 `h3` 구상을 실제 DOM의 기존 “대화” `h2` 아래에 맞게 정교화한 것이다.

```text
[상태 제목]
[한 문장 결과 또는 현재 진행 상태]

[핵심 업무 필드 또는 변경 전 → 변경 후]

[다음 행동]
```

- 상태 제목과 결과는 첫 두 줄 안에 둔다.
- screen reader heading 탐색에서는 `대화` `h2` 다음에 각 신규 업무 상태의 `h3`가 시간순으로 나타난다.
- 목록은 한 항목당 `ID | 제목` 다음 줄에 상태·우선순위·서비스를 둔다.
- 상세는 식별, 내용, 서비스·구성, 영향·긴급도, 상태·시각 순서로 묶는다.
- 등록·수정 확인은 전체 대상과 실행될 값, `확인`·`수정`·`취소`의 의미를 한 메시지에 둔다.
- 긴 텍스트는 `white-space: pre-wrap`, `overflow-wrap: anywhere`의 기존 동작으로 재흐름하며 조용히 잘라내지 않는다.

## State M1 — Loading

```text
USER
  [자연어 티켓 요청]

ASSISTANT · status
  티켓을 확인하고 있습니다.
  완료되면 이 대화에 결과를 알려드리겠습니다.
```

- 기존 `응답을 기다리는 중…` pending 메시지를 유지하되 요청 종류를 안전하게 식별할 수 있으면 `티켓을 검색하고 있습니다`, `등록 내용을 확인하고 있습니다`, `최신 티켓 정보를 확인하고 있습니다`처럼 구체화한다.
- 비밀정보, 원본 요청 본문, 내부 재시도 횟수는 표시하지 않는다.

## State M2 — Search Results, Empty, and Pagination

### Populated

```text
ASSISTANT · status
  티켓 검색 결과
  현재 권한 범위에서 [결과 수]건을 찾았습니다.

  1. [티켓 ID] | [제목]
     상태: [상태] | 우선순위: [우선순위] | 서비스: [서비스]

  2. [티켓 ID] | [제목]
     상태: [상태] | 우선순위: [우선순위] | 서비스: [서비스]

  다음 결과가 있습니다.
  “다음 결과” 또는 “[티켓 ID] 상세”처럼 입력할 수 있습니다.
```

### Empty

```text
ASSISTANT · status
  티켓 검색 결과
  현재 조건과 권한 범위에서 일치하는 티켓이 없습니다.

  검색어 또는 필터를 바꾸어 다시 요청해 주세요.
```

- 한 응답은 계약상 최대 100개이며 기본 20개다.
- `next_cursor`는 사용자에게 노출하지 않고 현재 대화의 같은 검색 조건에 결합한다.
- 조건 또는 정렬이 바뀌면 이전 cursor를 폐기한다.
- 긴 제목도 DOM 텍스트로 안전하게 재흐름하며, 의미를 보존할 수 없는 임의 말줄임은 하지 않는다.

## State M3 — Ticket Detail

```text
ASSISTANT · status
  티켓 상세 [티켓 ID]

  제목: [제목]
  설명: [설명]

  서비스: [서비스]
  컴포넌트: [값 없음 또는 값]
  모델: [값 없음 또는 값]

  영향도: [영향도]
  긴급도: [긴급도]
  영향 범위: [영향 범위]

  상태: [상태]
  발생 시각: [현지화된 시각과 시간대]
  최근 수정: [현지화된 시각과 시간대]
```

- 선택 필드가 없으면 `값 없음`으로 표시하며 추측하지 않는다.
- 404는 `티켓을 확인할 수 없습니다. ID를 확인하거나 다른 조건으로 검색해 주세요.`라는 동일한 안전 메시지로 처리한다.
- ITSM 텍스트가 명령문처럼 보여도 인용된 업무 데이터일 뿐 확인·신원·도구 동작을 바꾸지 않는다.

## State M4A — Create Input Collection and Validation

등록 review를 만들기 전에 필수값과 카탈로그 값을 대화로 수집·검증한다. 사용자가 이미 제공한 유효한 값은 보존하고, 부족하거나 잘못된 값만 다시 묻는다. 이 상태에서는 등록 요청을 보내지 않는다.

### Missing Required Value

```text
ASSISTANT · status
  티켓 등록 정보를 더 알려주세요.
  지금까지 입력한 유효한 내용은 그대로 보관했습니다.

  필요한 값: [누락된 필드 레이블]
  [필드별 허용 형태 또는 예시 형식]
```

### Ambiguous or Missing Time Zone

```text
ASSISTANT · status
  발생 시각의 시간대를 확인해 주세요.
  “[시간대가 포함된 시각]” 또는 “지금”처럼 알려주세요.

  다른 등록 정보는 그대로 보관했습니다.
```

### Catalog Name Needs Resolution

```text
ASSISTANT · status
  [서비스 또는 컴포넌트 또는 모델]을 하나로 확인할 수 없습니다.
  등록 요청은 보내지 않았습니다.

  [공개 가능한 활성 후보의 이름과 비밀 아닌 식별 정보]
  사용할 항목을 명확히 알려주세요.
```

### Catalog Value Invalid

```text
ASSISTANT · status
  요청한 [필드]은 사용할 수 없습니다.
  [미존재·비활성·서비스 불일치 중 안전한 설명]

  [안전한 활성 후보 또는 값을 찾는 방법]
```

- 누락·길이·enum·시간대 오류와 카탈로그 모호함·미존재·비활성·서비스 불일치에서는 POST 요청이 0회다.
- 각 질문은 필요한 값만 요구하며 이미 유효한 제목·설명·영향도·긴급도·영향 범위 등은 버리지 않는다.
- 후보는 현재 계약과 권한으로 공개할 수 있는 활성 항목만 제시하며 첫 항목을 추측 선택하지 않는다.
- 서비스와 컴포넌트의 관계가 맞지 않으면 두 값을 명확히 다시 확인한다.
- 모든 필수값이 유효하고 카탈로그 이름이 유일한 활성 항목으로 해석된 뒤에만 M4의 전체 review로 이동한다.

## State M4 — Create Review and Confirmation

```text
ASSISTANT · status
  티켓 등록 내용 확인
  아래 내용으로 새 티켓을 등록할 예정입니다.

  제목: [제목]
  설명: [설명]
  서비스: [서비스]
  컴포넌트: [값 없음 또는 값]
  모델: [값 없음 또는 값]
  영향도: [영향도]
  긴급도: [긴급도]
  영향 범위: [영향 범위]
  발생 시각: [시각과 시간대]
  분류: [값 없음 또는 값]

  확인 — 이 내용으로 등록합니다.
  수정 — 바꿀 항목과 값을 알려주세요.
  취소 — 등록하지 않습니다.
```

### Confirmation Handling

- 명백한 확인만 POST 실행으로 이어진다.
- `수정`은 변경 내용을 반영한 전체 요약을 다시 보여주고 새 확인을 요구한다.
- `취소`는 `티켓을 등록하지 않았습니다.`로 끝낸다.
- 단순 동의처럼 보이지만 대상이 불명확한 답, 조건이 붙은 답, 새로운 값이 함께 있는 답은 실행하지 않고 `등록, 수정, 취소 중 하나를 명확히 알려주세요.`라고 다시 묻는다.
- 사용자·세션·대화·본문 중 하나라도 바뀌면 기존 확인을 폐기한다.

## State M5 — Update Review, Conflict, and No-op

```text
ASSISTANT · status
  티켓 수정 내용 확인
  대상: [티켓 ID] | [제목]

  제목: [이전 값] → [새 값]
  영향도: [이전 값] → [새 값]
  [실제로 바뀌는 필드만 반복]

  확인 — 최신 version에 이 변경을 적용합니다.
  수정 — 바꿀 항목과 값을 알려주세요.
  취소 — 수정하지 않습니다.
```

### Conflict

```text
ASSISTANT · alert
  티켓을 수정하지 않았습니다.
  다른 변경이 먼저 적용되어 최신 내용이 달라졌습니다.

  최신 상세를 다시 확인한 뒤 변경 내용을 새로 검토해 주세요.
```

### No-op

```text
ASSISTANT · status
  변경할 내용이 없습니다.
  요청한 값이 현재 값과 같습니다. 티켓을 수정하지 않았습니다.
```

- PATCH는 확인된 version과 일치할 때만 보낸다.
- 충돌·결과 불명확 상태에서는 자동 PATCH 재시도를 하지 않는다.
- 사용자·세션·대화·대상·값·version 중 하나라도 바뀌면 기존 확인을 폐기한다.

## State M6 — Success and Safe Recovery

### Create or Update Success

```text
ASSISTANT · status
  티켓 작업 완료
  [티켓 ID]의 [등록 또는 수정]이 완료되었습니다.

  [허용된 업무 결과 요약]
```

### Rate Limited

```text
ASSISTANT · alert
  지금은 티켓 요청을 처리할 수 없습니다.
  자동으로 기다리거나 다시 요청하지 않았습니다.

  [검증된 Retry-After가 있을 때: N초 후, [다시 요청할 시점] 이후 다시 시도해 주세요.]
  [없거나 유효하지 않을 때: 잠시 후 다시 요청해 주세요.]
```

### Authentication Recovery Failed

```text
ASSISTANT · alert
  로그인을 다시 확인해 주세요.
  티켓 등록 또는 수정 요청은 실행되지 않았습니다.

  다시 로그인한 뒤 내용을 확인하고 요청해 주세요.
```

### Create Result Ambiguous

```text
ASSISTANT · alert
  티켓 등록 결과를 아직 확인할 수 없습니다.
  성공이나 실패로 추측하지 않았으며 새 등록을 시작하지 않았습니다.

  기존 처리 결과를 먼저 확인합니다. 확인되지 않을 때에만 원래 요청과
  같은 중복 방지 상태로 한 번 더 시도할 수 있습니다.
```

- 안전 오류에는 허용된 범주, 다음 행동, 필요한 경우 비밀이 아닌 request ID만 포함한다.
- 원본 problem detail, 예외 문자열, 헤더, 토큰, client secret, OpenAI API key는 표시하지 않는다.
- 등록 결과가 끝까지 불명확하면 추가 자동 등록을 중단했다고 명시한다.

## Responsive and Content Stress States

별도의 breakpoint를 추가하지 않는다. 기존 화면의 유동 너비와 줄바꿈을 기준으로 다음을 보장한다.

| Condition | Required rendering |
|---|---|
| 좁은 화면 | topbar와 사용자 선택기는 기존처럼 줄바꿈하고 대화 패널은 가로 스크롤 없이 축소된다. |
| 긴 제목·설명 | `.msg` 안에서 줄바꿈하며 컨테이너 밖으로 넘치지 않는다. |
| 긴 불투명 ID | `overflow-wrap: anywhere`로 줄바꿈하되 값은 변형하지 않는다. |
| 목록 1개 | 번호와 필드 레이블을 그대로 유지한다. |
| 목록 기본 20개 | 대화 로그의 기존 세로 스크롤을 사용하고 다음 페이지 안내를 마지막에 둔다. |
| 선택 필드 누락 | 빈 줄 대신 `값 없음`을 표시한다. |
| 200%·400% zoom | 정보 순서와 입력·전송 순서를 유지하고 가로 스크롤을 새로 만들지 않는다. |

## Out of Scope

- 새 화면, 시각적 카드, modal, 확인 버튼, 필터 패널, 별도 티켓 상세 화면
- 기존 색상·간격·타이포그래피·breakpoint의 재설계
- 삭제, 상태 전이, 담당자 배정, 댓글·첨부·작업 기록 UI
- 보이지 않는 티켓의 존재 또는 사용자의 권한 수준을 추측하는 문구
